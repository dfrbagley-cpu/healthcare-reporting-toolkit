# Security policy

## Supported version

Security fixes are applied to the latest release.

## Reporting a vulnerability

Use GitHub's private vulnerability-reporting feature under **Security →
Advisories** when it is available. If that option is unavailable, open a
minimal public issue asking the maintainer to establish private contact; do not
include exploit details, sensitive data, or personal health information.

## Data handling

The published application is static. CSV files are parsed in the browser and
are not uploaded by the toolkit. The site has no analytics, account system,
server-side storage, or network API.

Extract analysis receipts include SHA-256 source fingerprints and aggregate
metadata, but exclude filenames, headers, row keys, and cell values. A hash is
not anonymization and does not prove who supplied a file or when it existed.
The separate change-log CSV contains row-level differences and can retain the
sensitivity of the source extracts. Review all downloaded artifacts before
storing or sharing them.

Reporting-results receipts likewise exclude filenames, result keys, metric and
quality identifiers, actual and expected values, and row diagnostics. They do
include source hashes, the public synthetic case ID, contract provenance, and
aggregate mismatch counts. The separate diagnostics CSV contains exact result
keys and values and can remain sensitive.

The Receipt Inspector parses no more than 256 KB of strict JSON and recognizes
only published receipt profiles. Optional source verification reads files
locally, enforces the same role-specific limits as the producing tool, and
compares exact byte counts and SHA-256 fingerprints. It never uploads, persists,
or copies source content into its results; selected browser `File` references
remain in the tab until the user clears them, selects a new receipt, or closes
the tab. A matching unkeyed digest or source hash does not authenticate a
person, establish provenance, or prove a creation time; selected filenames and
inspection results are visible in the local browser.

The conformance catalog is generated by and pinned to Health Data Edge Cases.
The deployed application uses its vendored copy and makes no runtime network
request for contracts. CI verifies the byte-identical catalog, generated module,
release version, and SHA-256 digest.

Users should still follow their organization's privacy, security, retention,
and data-handling policies. Inspect the source and deployment before using any
local copy with sensitive information.
